# Travel Calendar Roadmap

Updated: 2026-10-29 · Owner: Travel Calendar · North star: Be the Stripe of travel calendars. Travel Calendar is calendar memory for agents, built for couples. Two people and their agents share one trusted trip calendar as the system of record. Intent goes in, and one plan comes out. Agents are the main way the product is used. People use it through MCP tools, and equivalent agent tool interfaces, on marketplaces where they already live. Those hosts include Muse marketplace, Grok marketplace, and Claude or ChatGPT MCP hosts. The website UI still ships and matters for glance, confirm, couple invite, and the agents plane, but it is secondary. Marketing leads with agent-native MCP or web that syncs with wherever you keep your calendars. Optional Google Calendar and Apple Calendar export is Later. Every user-facing system-of-record action in the website UI must also be reachable through MCP tools. No UI-only dead ends for core SoR actions. It is not a chat app, not a booking engine, and not another AI itinerary planner. Couple and shared-trip SoR stays the wedge. Travel Calendar owns the couple's trip memory and reaches people through MCP.

Say "what's good near X," and add that plan to the shared trip both people see. The object is that calendar, shaped by time. It is not a markdown trip file, and it is not a day-board. Humans set intent. An agent proposes a shared-plan change, and a partner accepts it onto the shared calendar before both people treat it as the plan. The shared calendar stays the source of truth. Personal calendars only receive a copy. A plan row shows who proposed it and who confirmed it. Distribution is a host skill file on the agent marketplace each partner already uses, once the MCP write contract holds. Travel Calendar lists that skill. It does not broker other products.

8. **Trip and item tools, with propose then confirm.** Ship step 1, next to the Open item 4 write contract. An agent proposes a shared-plan change. 10. **Couple trip memory tools.** Ship step 3. `memory.search` and `memory.export` read the couple's trip memory. They do not write to Google Calendar or Apple Calendar. `memory.pin` stays Later. Check: `memory.search` returns plans from the shared trip, and `memory.export` returns that memory without an external calendar write.

## Not doing

- A different-backend rewrite. The current Convex app is the product.
- A multi-trip team product before couple and partner flows work.
- Booking and reservations for flights, hotels, and restaurant checkout. The product is the shared trip system of record. Users or other agents book elsewhere, and the calendar holds the plan.
- A generic solo itinerary planner, such as LetsPackUp, PlanGoGo, Traveler.md, or aitrips. Those are a markdown trip file or a day-board for one person. The unit here is a couple, and the object is one shared calendar.
- Free-form hex pickers and per-card colors. Couples pick a named theme pack. Agents and partners stay on one shared look.
- A marketplace broker, or arbitrage between host listings. Travel Calendar lists its own skill. It does not sit between other products.
- Chat as the primary way to use the product. The website is glance and confirm. The host skill returns a summary card, not a transcript.
- Soft mush, pastel lifestyle chrome, or low contrast as the hero look.
- Trip chat as a second system of record.

## Anti-patterns

- A site form writes shared trip truth and has no MCP twin.
- A host auto-confirms when the grant is only propose.
- A free-text itinerary stands in for structured item fields.
- Booking checkout runs inside Travel Calendar.
- Confirm UI hides who owes confirm.
